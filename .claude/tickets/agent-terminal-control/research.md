# Research: agent terminal control via MCP

## Question
What does a planner need to know to add terminal-control MCP tools (open/run/send/read/list/close), agent-marked tabs, a "Home" sidebar entry, and a Settings toggle, on top of the current PTY, tab, MCP, location and settings code?

## Answer
- The renderer owns everything about a terminal. It picks the id (`crypto.randomUUID()`), creates the xterm, and asks main to spawn the PTY via `pty:create`. Main only holds a `Map<id, IPty>` plus per-webContents ownership. Main has no output buffer and no exit-code store; data goes straight to the owning webContents.
- There is exactly one main->renderer push channel for app state (`state:changed`, whole `AppState`). There is no "open a tab" or "write to pty" push. Both must be added (new IPC channels plus a preload API), together with a request/response round trip for results.
- `read_terminal` is easiest from a main-side ring buffer fed in the pty `onData` handler (must be added). Output is raw ANSI/ConPTY bytes. The renderer's xterm buffer is the only rendered screen.
- The saved-command runner is NOT reusable for `run_command` in a live shell. It spawns a one-shot process (`spawnSteps`) whose real process exit code is the result. No sentinel exists anywhere. `run_command` in an interactive pwsh needs a new sentinel technique, or a new one-shot steps tab.
- A "Home" location does not fit the current location model: every location is a folder or group id with a saved path, and `pty:create` rejects any cwd outside saved roots.
- Settings are simple to extend (schema + dialog field) and main can read them (`store.getSettings()`).
- `yarn typecheck` passes (details in section 6).

## 1. PTY lifecycle
- Spawn paths in `src/main/pty.ts`: `spawnPty` (`:73-92`, calls `pty.spawn` with `name: 'xterm-256color'`, `env = process.env + extraEnv`), wrapped by `spawnShell` (`:95`), `spawnElevated` (`:107`), `spawnSteps` (`:120`). **confirmed**
- Only caller in the app is the `pty:create` handler `src/main/index.ts:437-513`. The smoke test also calls them directly (`src/main/smoke.ts:40,70`). **confirmed**
- Id/key: `req.id` is chosen by the renderer (`App.tsx:284` `crypto.randomUUID()`). Main stores `ptys: Map<string, IPty>` (`index.ts:36`) and rejects duplicates (`:454`). **confirmed**
- Ownership: `owners: Map<webContentsId, Set<id>>` (`index.ts:38`). `pty:write/resize/kill` are accepted only from the owning sender (`:514-528`). A reload, crashed renderer or destroyed window kills that renderer's PTYs (`:144-151`). **confirmed**
- Consequence: a main-initiated `pty.write` for an agent is fine in-process (the `ptys` map is in main). But PTYs only exist if the renderer created them, so an agent-opened terminal must be created through the renderer (or main must spawn and register ownership itself).
- Output flow: pty `onData` -> `e.sender.send('pty:data', id, data)` (`index.ts:478-480`) -> preload `onPtyData` (`preload/index.ts:83-87`) -> `termRegistry.ts:175` `entries.get(id)?.term.write(data)`. Input flow: xterm -> `ptyWrite` -> `ipcRenderer.send('pty:write')`. **confirmed**
- Buffer in main: none. `rg` shows no scrollback/ring buffer in main. Scrollback lives only in xterm (`settings.scrollback`, default 5000, `shared/settings.ts:46`), and is not persisted ("Scrollback ... not restored", README). **confirmed**
- Exit codes: `onExit` (`index.ts:481-492`) cleans maps and sends `pty:exit(id, code)`. Renderer prints `[process exited with code N]` (`termRegistry.ts:190`) and calls `handleExit` (`App.tsx:443`). For shell tabs it only sets `exited: true` (code dropped, `:447-449`); for command tabs it stores `run.exitCode`. Main discards the code after forwarding. **confirmed**
- Cleanup detail: once released by kill, `onExit` still reports the exit (`:485`); a stale exit from an old pty reusing an id is ignored (`:484`).
- Shell: `store.getShell()` -> `resolveShell(settings.shell)` (`store.ts:299`, `pty.ts:16-22`): empty = `pwsh.exe` on PATH else `powershell.exe`. The renderer may request another shell only if it is the configured one or a known available one (`index.ts:455-462`). Interactive shells run with no args (`pty.ts:103`), so the user's PowerShell profile and PSReadLine load. **confirmed**
- Admin: `elevated:true` in the request -> `resolveElevator` (gsudo, or Windows sudo in `normal` mode, `elevation.ts:51-59`) -> `elevatedCommand` -> `gsudo --direct <shell> -NoLogo` (`elevation.ts:94-102`). Rate limit 1500 ms per webContents (`index.ts:465-470`). Elevated requests with `steps` are refused (`elevation.ts:105`). On kill an elevated shell first gets Ctrl+C + `exit\r`, real kill 400 ms later (`index.ts:84-91`). UAC prompt comes from the click; an agent-driven elevated open would prompt UAC without a user click (inferred; recommend not exposing admin to MCP).
- cwd choice: renderer sends `cwd` (location path, or an override); main requires an existing directory that `store.isInsideRoots(c) || store.isCommandCwd(c)` (`index.ts:443-447`). On failure for non-steps requests it falls back to `req.fallbackCwd` (`:451`). **Home (Documents) is neither a saved root nor a command cwd, so it is rejected today.**
- Env per terminal: `TERMINALS_MCP_URL/TOKEN/LOC_ID/LOC_PATH` via `ptyEnv(locId)` (`index.ts:300-308`); `locationById` must resolve the id or the loc vars are empty.
- Size: cols/rows come from the xterm after `fit()` (`TerminalView.tsx:46-53`); main clamps min 2x1 (`index.ts:494`).

## 2. Tab model
- `Tab` is a renderer-only type in `TabBar.tsx:11-39` (id, locId, cwd, title, kind `shell|command|diff|file`, shell, startCwd, exited, elevated, pending, run...). **confirmed**
- All tabs are created in `App.tsx` and held in `tabsRef/useState` (`:115-116`, `commitTabs :150`). `newTab(locId, cwdOverride?, paneId?, elevated?)` (`:277-300`) calls `createTerm(id)` (xterm in `termRegistry.ts:221`) and appends the tab; `showTab` activates it. The PTY is spawned later, when `TerminalView` mounts and `term.open()` runs (`TerminalView.tsx:40-68`, `entry.started`).
  - Consequence: a tab needs a mounted, laid-out TerminalView to get its PTY and cols/rows. `safeFit` skips when width/height is 0 (`:28`). Behaviour of a tab opened while the window is hidden in the tray, or in a non-visible tab, is **inferred** (TerminalView is mounted for the tab's whole life, hidden by CSS, per its doc comment `:36`); needs a real-app test.
- Tab -> location: `tab.locId` (sidebar entry id). Tab bar and panes filter by locId (`shared/tabs.ts`, `panes.ts`). Tab -> PTY: same id (`tab.id` == pty id == `createTerm` id). Tab -> cwd: `tab.cwd` + `startCwd`; live cwd only via OSC 7 / 9;9 (`App.tsx:123`).
- Persistence: renderer-driven. `scheduleSave` (`App.tsx:166-175`) debounces 300 ms and calls `setUi({panes, tabs: toPersistedTabs(...)})`; main sanitises with `sanitizeTabs` (`shared/session.ts:50`), keeps <= 200 tabs. `PersistedTab` has no "agent" flag (`shared/types.ts:40-58`); sanitize copies only known fields, so a new field must be added in `types.ts`, `sanitizeTab`, `toPersistedTabs`, `SessionTab`, and the restore mapping at `App.tsx:578-606`.
- Restore (`App.tsx:550-640`): shell tabs get `createTerm` and start a fresh shell in saved cwd; locations that are gone or missing are skipped (`session.ts:117`). A Home tab needs a location that `planRestore` can find in `locs`.
- Main -> renderer today: only `state:changed` (`index.ts:292-294`, listener `App.tsx:844-860`, preload `preload/index.ts:8-12`) and `fs:changed`, `pty:data`, `pty:exit`. MCP mutating tools trigger `pushState` via `onChange` (`mcp.ts:82-85`). The renderer reacts to a pushed state only by closing tabs of removed locations and `setState(next)`. **No existing way for main to ask the renderer to open a tab.** Options: (a) new channel `tabs:open` main->renderer (e.g. `{ id, locId, cwd, agent: true }`) with the renderer calling `newTab`, plus a reply channel so the MCP call can await creation/PTY start; (b) put a "pending agent tabs" list into AppState and let the renderer diff it in the `onStateChanged` effect (reuses `pushState`, but state is also persisted via the store, so keep it out of `terminals.json`).
- Single window only: `win` is one `BrowserWindow`; closing hides to tray (`index.ts:162-167`, `showWindow :175`); `pushState` and the `ownsPty` model assume one window. Hidden window: the renderer keeps running (inferred).

## 3. MCP
- Server: `src/main/mcp.ts`. A new McpServer + stateless Streamable HTTP transport is built per request (`:64-119`); tools come from `TOOLS` in `mcpTools.ts`. Handler is sync: `t.run(args, ctx)` (`mcp.ts:76`), `ToolDef.run` returns `unknown` (`mcpTools.ts:341-349`). **A `run_command` that waits for completion needs `run` to be async (`await`) - the call site must change to `await t.run(...)`; the type allows a Promise at runtime but not signalled.**
- `ToolContext = { headerLocation?, dataDir }` (`mcpTools.ts:31-35`). No access to webContents/ptys; any terminal tool needs a new dependency injected (e.g. a `TerminalHost` object passed through `startMcpServer` -> `handle` -> `buildServer` -> ctx). `startMcpServer` opts today: `{ dataDir, version, onChange }` (`mcp.ts:136`), called at `index.ts:545`.
- `defineTool({ name, description, shape (zod), mutates, destructive, run })` (`mcpTools.ts:351`). `mutates` triggers `onChange` -> `pushState` in `finally` (`mcp.ts:82-85`). `annotations: readOnlyHint = !mutates` (`:72`). Errors: throw `ToolError` -> returned as `isError` text (`:78-81`); others become "Internal error".
- Location resolution: `findLocation(state, ref, kinds?)` (id, absolute path of a saved folder/group/child, unique name; `mcpTools.ts:81-111`), `contextLocation` (explicit arg else the `X-Terminals-Location` header, `:114-125`). Built on `buildLocations(state)` (folders, groups, children; `:48-61`). The header name is `x-terminals-location` (`mcp.ts:18`), read at `:109-110`. Unknown absolute paths are an error, never auto-added; this is stated in README and tests, so `open_terminal` with "a path" needs a decision (see Open questions).
- Instructions string says "Nothing here runs commands" (`mcp.ts:27-28`), README says the same (README:82). Both must be updated, and the tool set should be registered only when the toggle is on (or each tool should throw a `ToolError` when off). Tools are registered per request, so a toggle change takes effect on the next request without restart (`buildServer` per request; reading the setting at that time works).
- Security: loopback + bearer token + Host/Origin checks (`mcp.ts:100-105`). The README states anything running as the user can read the token (`README:125`), so the toggle is the only barrier. Plan for a default-off setting and an explicit error message.
- Tests: `smoke.ts:592-729` `checkMcpLogic` covers location resolution, command/prompt validation and `hostAllowed`/`tokenMatches` against a synthetic state; it does not start the HTTP server nor the renderer. `checkPtyEnv` (`smoke.ts:442+`) checks env vars. No end-to-end MCP test exists. **confirmed**

## 4. Saved-command runner and completion detection
- Mechanism: `buildRunArgs` (`pty.ts:57-71`). For pwsh/powershell it builds a script: each step then `if (-not $?) { $__c = if ($LASTEXITCODE) { $LASTEXITCODE } else { 1 }; break }`, ends with `$host.SetShouldExit($__c)`, passed as `-NoLogo -NoProfile -EncodedCommand <base64 utf16le>`. cmd: `/d /s /c step1 && step2`. Deliberately no `exit` (comment `:60-62`: PowerShell buffers formatted output and `exit` drops it).
- Completion/exit code = real process exit: `pty.onExit(e.exitCode)` (`pty.ts:90`) -> `pty:exit` -> `handleExit` (`App.tsx:443-460`) sets `run.status` success/failed. Smoke check 2 asserts `Write-Output ('a'+'1')` then `exit 3` gives code 3 (`smoke.ts:59-83`). **confirmed (read; I did not run `yarn smoke`)**.
- No sentinel/marker technique exists in the runner. The only marker trick is in smoke check 1: the command builds the marker by concatenation (`'smoke-' + 'ok'`) so the echoed input line can never match; only real output does (`smoke.ts:43-45,54`). Smoke uses a `1500 ms` delay before writing to let the shell start (`:55`).
- Reusability for `run_command`:
  - One-shot variant (open a command-kind tab/pty with `steps`): exit code exact, no sentinel needed, tab ends with output and `✓/✗` line; but not "in" an interactive shell (no cwd/env state shared) and PowerShell `-NoProfile` is used. Agent runs that exit when done fit "run command, wait, return output + exit code" well. The `cwdError` check skips the roots rule for `steps` only via `isCommandCwd` (`index.ts:445`).
  - Interactive variant (write into a live pwsh): needs a sentinel. Quirks (inferred from the code/comments, not tested): ConPTY echoes the typed line, PSReadLine redraws it with escape sequences and cursor moves (smoke comment `:43-44`), output is ANSI-heavy, long lines wrap at the terminal width (cols from fit), and pwsh `$LASTEXITCODE` is only set by native programs while `$?` covers cmdlets. A robust form is to write a command that prints a concatenation-built marker with `$LASTEXITCODE`/`$?` (so the echo cannot match, as in smoke), and strip ANSI before parsing. Multi-line input and bracketed paste (`term.paste`, `termRegistry.ts:212`) are other differences between typed and pasted input.

## 5. Locations and settings
- Location ids: folders and manual/parent groups use `randomUUID()` (see `store.ts`, `mcpTools.ts:233` pattern); parent-group children have an id derived from the path (`shared/types.ts:88` comment, README:55). Renderer `buildLocs` (`locations.ts:16-34`) and main `buildLocations` (`mcpTools.ts:48-61`) are two parallel builders over `AppState`; both must learn a Home entry (or Home must be injected into `AppState`).
- Where a location id is used: `Loc.kind` is `'folder'|'child'|'parent'|'manual'` (`locations.ts:10`, `mcpTools.ts:14`); `selectedId`, panes (`PersistedPanes.locIds`), tab `locId`, command/prompt `ownerId`/`scope`, `TERMINALS_LOC_ID`. Layout normalisation drops locations not in `locs` (`App.tsx:219-230`) and session restore skips tabs of unknown locations (`session.ts:117`).
- Sidebar: `Sidebar.tsx` renders `state.folders`, `state.groups` (+ children), shows `missing` state, per-location live counts `counts[id]` (`App.tsx:826-833`: live tabs per locId, exited ones not counted), and "New terminal" via `onOpenTerminal` -> `openTerminal` = `select(id)` + `newTab(id)` (`App.tsx:322-328`). A pinned Home row needs its own markup (above the lists), a stable id (e.g. `home`), `counts['home']`, and handling for `selectedId` (selection is persisted as `data.selectedId`, `store.ts:581-584`, and store code falls back to first folder/group when the selection is removed, `:398-401,443`).
- Missing checks: `missing` is computed in `store.getState` from `existsSync` (`store.ts:258-281`). A Home dir should do the same.
- Security/path rules in main that would block Home: `pty:create` cwd rule (`index.ts:443-447`), `store.isInsideRoots` for fs/files panel/git (`index.ts:311-313`, `fsops`), Files panel and Git panel use the selected folder path. Decide whether Home gets the Files/Git panels (it would require adding the Home dir to the allowed roots).
- Settings: `Settings` interface `shared/types.ts:8-20`; `SETTINGS_SCHEMA` with `default` + `sanitize` per key (`shared/settings.ts:20-47`, TypeScript forces a schema entry per key); `sanitizeSettings` (load) and `patchSettings` (update) are generic over the schema. Persistence: `store.setSettings` (`store.ts:662-666`) -> `save()` -> `terminals.json` atomic write (tmp + rename, `store.ts:218-222`). Existing booleans: `cursorBlink` (toggle kind). Schema version `SCHEMA_VERSION = 4` (`types.ts:2`); adding a key with a schema default needs no migration (missing key -> default in `sanitizeSettings`), so a version bump is probably not required (inferred from `sanitizeSettings` using defaults).
- Dialog: `SettingsDialog.tsx` has a declarative `SECTIONS` table with `FieldDef` kinds `select|number|toggle|text` (`:16-78`). A directory-path field needs either a `text` field plus a new "browse" button using the existing `window.api.pickFolder()` (`preload/index.ts:44`, `index.ts:285-289`), or a new `kind: 'path'`. A toggle with a danger hint fits `kind: 'toggle'`. The reset button resets appearance only (`:300`; check which keys it touches).
- Main can read settings anywhere: `store.getSettings()` (`store.ts:295`); `mcpTools.ts` already imports `store`. The default Documents dir: `app.getPath('documents')` (not used anywhere yet; `rg` found no hit); better default at runtime than stored, since the schema default is a static value (the sanitizer cannot call `app`).
- README documents the settings shape and says "There is no settings UI; edit the file" (`README:145,153`), which is already stale (there is a dialog). Update docs.

## 7. Risks and seams
1. Renderer owns xterm and the PTY lifecycle: main cannot read the rendered screen. Reading "last N lines" from main means a new raw-byte ring buffer, which contains ANSI, cursor moves and redraws, so line semantics are poor (needs an ANSI stripper / VT parser). Alternative: ask the renderer to serialise `term.buffer.active` lines (needs a request/response IPC; `@xterm/addon-serialize` is not a dependency). Main's raw buffer would work with the window hidden.
2. Round-trip needs: the MCP HTTP handler lives in main, the tab creation in renderer. `open_terminal` must await the renderer (new id, PTY started, errors like cwd rejected) with a timeout; hidden window or reload must produce a clear error. Renderer reload kills all PTYs (`index.ts:147-148`), which invalidates agent terminal ids (list_terminals must reflect that).
3. Id ownership: `pty:write/resize/kill` require `owners` membership by the sender. Agent input and close from main bypass IPC, but must reuse `releasePty(id)` (`index.ts:71`) for correct cleanup; `renderer closeTab` is where the tab itself disappears, so close must also tell the renderer (otherwise a dangling tab remains in an `exited` state).
4. Exit codes for interactive shells: a tab only exits when the shell exits; `run_command` exit code needs the sentinel (section 4) or a one-shot steps pty. Handling of long-running/interactive TUIs, timeouts, and a command that never returns needs a timeout design.
5. Security: the token is readable by any same-user process (README:125), and the toggle is the only guard; all new tools should check the setting at call time and tool descriptions/instructions (`mcp.ts:27`) and README ("deliberately no tool that runs a command", README:82) change. Admin (`elevated`) should not be exposed to MCP (UAC without a click).
6. Unicode 11 widths (`termRegistry.ts:233-235`) affect wrapping in the renderer; a main-side raw buffer does not know widths, so "last N lines" from main may differ from what the user sees for wide chars.
7. gsudo-elevated terminals: `--direct` ConPTY child is a separate elevated process; `list_terminals` should mark them; `releasePty` sends Ctrl+C/`exit` first. Writing into them from an agent is a privilege-escalation path if the user opened admin tab, so consider refusing agent input to elevated ids.
8. Single instance (`requestSingleInstanceLock`, `index.ts:533`), single `win`; the tray hides the window rather than closing it, so the renderer is alive but invisible. `showWindow` is not called by MCP; decide whether an agent-opened terminal should raise the window.
9. Home location touches: `buildLocs`, `buildLocations`, `Sidebar`, `counts`, `normalize`/pane code (valid ids come from `locs`), `planRestore`, `pty:create` cwd rule, `store.getState` (missing), selection fallback in the store, `ptyEnv/locationById`, fs/git root checks. Missing the id in any of the two location builders makes tabs vanish at restore or get empty `TERMINALS_LOC_ID`.
10. Agent mark in the tab: `Tab` + `PersistedTab` + `sanitizeTab`/`toPersistedTabs`/restore (section 2); restore starts a fresh shell, so decide whether agent tabs are persisted at all (session restore re-creating agent tabs after restart with no agent attached is probably not wanted).
11. Shared-code blast radius: `mcpTools.ts` `ToolDef.run` signature, `startMcpServer` opts, `TerminalsApi` in `shared/types.ts` + `preload/index.ts` (+ `preload/index.d.ts`), `PtyCreateRequest` all need coordinated edits; smoke has no renderer coverage, so tab-opening must be verified manually in the real app (run via `--data-dir` with a separate MCP port, README "Isolated data directory").

## Open questions
- `open_terminal` with a path: README rule says unknown paths are never added implicitly (`mcpTools.ts:97-99`). Should an arbitrary (unsaved) path be allowed (needs an `isInsideRoots` / `cwdError` exception), or only saved locations plus Home? Which `locId` would such a tab belong to?
- Should Home appear as a real location (selectable, with its own tab list, Files/Git panels, commands) or only as a launcher that opens tabs under a special location?
- Where should agent tabs live when the target is Home or a path (which sidebar entry's tab bar)?
- Interactive-shell `run_command` (sentinel) vs one-shot steps tab: which semantics does the feature want (state persistence across calls such as `cd`)? Not decided.
- Does an agent terminal survive window hide (tray)? Hidden-window layout/fit behaviour was not tested (needs the real app).
- Should agent-opened tabs persist across restart (see risk 10)?
- Not run: `yarn smoke` (build required by the script), so the claim "smoke passes today" is unverified.
